## 修复推进信息与执行证据的关系

- `test-report.md` 将 300 条分析样本分为检测通过、产品缺陷、不可用等类别。

这些信息可用于判断“为什么没有结果”，但不能替代逐 Case 机器结果。尤其是上述 139 个 Case，需要后续重新执行或补齐逐 Case 结果文件，才能确认是否真的执行过。

## Gap 汇总

1. **全集执行覆盖 Gap**：369 个中 139 个没有逐 Case 结果，缺口率 `37.7%`。
2. **统计口径 Gap**：当前存在 202、245、284、297、300、369 等多个总数，分别来自 Harness、汇总、校验、分类和全集，缺少统一的 Run Manifest。
3. **重复执行识别 Gap**：同一 Case 出现在多个 failure 目录和 summary 中，但没有统一的 `case_id → run_id → attempt → verdict` 台账；目前只能从文件和 `phase02_run` 反推。
4. **PASS 结果留存 Gap**：最新批次主要保存失败结果，因此“最新 PASS”可能是旧批次结果，不能证明最新批次未执行或仍通过。
5. **修复闭环 Gap**：文字报告记录了“已修复/待复测”，但没有为每个修复项建立明确的复测结果和时间戳。
6. **触发器/环境 Gap**：分类报告显示不少用例需要 `workflow_dispatch`、PR、评论、fork 或特殊 token，无法仅靠当前 API/Harness 直接触发；这部分应区分“未执行”“无法触发”和“执行失败”。
